# ADR-001 · 渲染引擎选型：Phaser 3 vs 原生 Canvas

> 状态：**已定稿** · 2026-11-21 · 程基岩（engineering-lead）
> 决策委托来源：decisions.md D0（技术栈：Web，Phaser / 原生 Canvas 二选一，**由本 ADR 定稿**）+ Phase 3 任务派发（P3-EL-001）
> 约束输入：8 册 GDD（接口冻结）、美术圣经 v0.5 §0/§4/§5/§8/§9/§10

---

## 上下文

v1 全部渲染需求（从 GDD 与美术圣经抽取）：

1. **13 槽分层合成**：512×1024 逻辑画布上 ≥13 张大尺寸透明贴图按固定层序叠加（paperdoll-render §2.1），全槽最大件宽达 512px；
2. **常驻微动效**：呼吸（3s 周期躯干缩放）为**每帧连续重绘**（D1-11 白名单 3 项）——不可用"脏区静止 + 事件重绘"策略回避；
3. **正/背双视图懒加载**：300ms 过渡窗口内预载目标视图 ≈13 张贴图、完成后卸载旧视图（D2-01）——需要成批纹理生命周期管理；
4. **房间 Y 排序**：21 锚点家具按 base-y 遮挡排序，仅摆放事件时变化（room-decoration §4）；
5. **性能红线**：60fps 目标 / 30fps 容忍（paperdoll-render §4），手机优先（D0），DPR=3 高端机在列（CAL-04）；
6. **动效纪律**：全部反馈动效 ≤300ms、可被下一操作打断、无队列（D1-11 / 美术圣经 §8）——需要可中断补间系统；
7. **触屏交互**：横向拖拽翻转、抽屉两档拖拽（速度吸附 0.5px/ms）、点按——需要手势识别与触控目标管理；
8. **部署**：静态 HTTP 托管、无服务端（D1-13 / 任务派发口径）；
9. **维护者现实**：后续代码由 AI 生成 + 少量人工评审——**框架生态成熟度 = 生成代码正确率的直接变量**。

## 备选方案

### 方案 A · 原生 Canvas 2D 自研微引擎

- 渲染：Canvas2D `drawImage` 逐层光栅化。
- **致命项**：呼吸动效强制每帧全量合成。DPR=3 设备上单层 512×1024 逻辑 → 约 4.7M 设备像素，13 层 × 60fps ≈ **每秒 3.7G 像素 CPU 光栅**，中端 Android 完全不可行；即便按 ADR-003 将渲染上限压到 2×，仍是每秒 1.6G 像素的 CPU 路径。Canvas2D 无硬件批合成，此路线与 60fps 红线直接冲突。
- 附带成本：需自建纹理加载器/解码调度/缓存驱逐（双视图懒加载的全部基础设施）、补间引擎（可中断语义）、手势系统、Y 排序——估算 2~4 周等值工程量，且全部为**一次性私有 invariant**，AI 生成代码在自研框架上的正确率显著低于成熟框架。
- 优点：零依赖体积；无框架升级耦合。

### 方案 B · PixiJS（WebGL 渲染库）+ 自组装

- 渲染性能与 Phaser 同级（WebGL 批渲染），包体更小（≈ 450KB min / ≈ 130KB gz）。
- 但 Pixi 只给渲染层：手势（拖拽翻转/抽屉速度吸附）、可中断补间、场景结构、纹理生命周期管理仍需自建——省掉的是三条路线中**风险最低的一块**（批渲染），留下的是**工程量最高的一块**（输入/动效/加载）。对本项目是错配：本项目难点不在绘制而在纹理内存治理与动效纪律。

### 方案 C · Phaser 3（WebGL 优先 + Canvas2D 自动回退）

- 渲染：WebGL 批渲染，13 层大贴图合成一次 draw call 级别；低端机 WebGL 不可用自动回退 Canvas2D（配 ADR-003 的 1× 渲染降档，落在 30fps 容忍线内）。
- 双视图懒加载：Loader + TextureManager 原生覆盖（按 key 载入/移除，`textures.remove` 即释放 GPU 纹理）——与 D2-01 懒加载语义一一对应。
- 动效：Tween 系统（`tween.killTweensOf` 天然实现"新事件到达即中止当前动效"的打断语义）；`prefers-reduced-motion` 在动效服务层统一裁剪。
- 输入：内建拖拽（含速度阈值）与点按，9.3 触控冗余两路径等价接入。
- Y 排序：`depth = base-y` + 摆放事件时 `sortChildren`，零每帧成本。
- 体积：官方 min 构建 ≈ 1.1~1.2MB 原始 / **≈ 350KB gzip**（静态托管开 gzip/brotli 后），首次加载由开场加载插画承接（美术圣经 §7 场景③天然兼任加载屏）；长缓存后二次访问零成本。
- 生态：文档/示例/社区体量最大，AI 生成代码正确率三者最高。

## 决定

**采用 Phaser 3（方案 C），版本钉定 3.90.0「Tsugumi」**（Sprint 1 开工首日经 G-01 复核由 3.88.x 升档——v3 树末版、3.88 的官方 drop-in 替代、零破坏性变更，详见文末 v1.0.2 补丁记录；后续升级仍必经 checklist §4 三步纪律）。

配套技术细节（不改变 D0 拍板栈，均为实现层选择）：

- 语言 **TypeScript**：13 槽表/21 锚点表/静态配置表全部强类型化，防 AI 生成代码漂移；
- 构建 **Vite** → 纯静态 `dist/`；
- 禁用范围：Phaser 物理、Tilemap、摄像机多路——本 ADR 只启用渲染/输入/补间/加载四族（**v1.0.1 补丁：增补 Sound 族，见文末补丁记录**）。

## 后果

**正向**
1. 60fps 红线在 DPR≤2 渲染口径下有硬保证（GPU 批合成 vs CPU 光栅是数量级差）；
2. 双视图懒加载、动效打断、Y 排序、手势四项全部用内建能力，Phase 5 实现量收敛到玩法逻辑本身；
3. Canvas2D 自动回退给"低端机 WebGL"风险留了免费兜底路径。

**负向与缓解**
1. 包体 ≈350KB gz —— 缓解：静态资源长缓存（immutable hash 文件名）+ 开场加载插画过渡，4G 下首屏 TTI 预算 ≤3s（checklist.md 红线 R-09）；
2. 框架升级耦合 —— 缓解：版本钉死在补丁线内，不追 minor 新特性；升级必经回归清单（checklist.md §4）；
3. Phaser Scale 管理器与"9:16 基准 + 长屏自适应 + 安全区"（hud-layout §5.1/5.7）需手工组装 —— 缓解：架构文档 §5 定死缩放管线（RESIZE 模式 + 手动逻辑坐标系），不使用 Scale.FIT 信箱模式；
4. 首次加载需网络 —— 本就是 Web 部署前提（D0 拍板 Web 栈时已接受），不构成新增产品级影响。

**需用户拍板项：无** —— 引擎二选一已由任务派发明确授权本 ADR 定稿；包体增量未改变体验与商业模式（v1 免费无内购，D2-06）。
